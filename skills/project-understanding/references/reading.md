# 怎么读项目

功能点从代码入口得到，不从文档目录得到。没有 `docs/` 也能做完前两遍。

## 功能点

一个参与者或外部系统能触发、并且产生可观察结果的能力。

入口是：路由、页面、命令、消息消费者、定时任务、设备回调、公开 API。私有方法、工具类、中间件不是功能点，记入结构文档。

## 三遍

每一遍都有停止条件。不要在第一遍读实现，不要在第二遍沿调用链一直往下读。

### 1. 边界

先看工程清单和启动项目，确认有几个可运行单元、什么技术栈。然后只收集入口，不读函数体。

每个候选记录：入口路径、名称、所在模块、一句话猜测的用户目标、状态 `unread`。同一资源或同一用户目标上的入口归成一组。

跳过这些目录的正文：`.git/`、`bin/`、`obj/`、`node_modules/`、`dist/`、`build/`、`.gradle/`。

这一遍的产物是功能候选清单。`inventory` 到这里结束。

### 2. 行为

对每个候选只读三样：入口处理函数、它直接调用的领域或服务方法、它写入的模型或表。能写清「触发 → 规则 → 状态变化 → 结果」就停。

同一组入口合成一张功能卡。读完的候选把状态从 `unread` 改成 `references/model.md` 里的证据等级。

### 3. 文档对照

仅当仓库里有 README、`docs/` 或注释在描述行为时才做。先有代码清单，再用文档去对。

文档是待验证的主张，代码是证据。每条相关陈述用下面一种结果：

| 结果 | 含义 |
| --- | --- |
| `matches` | 代码入口和文档说的是同一行为 |
| `stale` | 文档描述的行为代码里已经没有 |
| `unimplemented` | 文档承诺了行为，但没有对应入口 |
| `undocumented` | 代码有入口，文档没写 |
| `conflict` | 文档和代码对同一行为的说法对不上 |

卡片状态按 `references/model.md` 判定。上表里除 `matches` 以外的结果只进文档对照表，不写进功能卡正文。没有这类文档就跳过这一遍，并在索引里写「无项目文档」。

## 第一遍找不到入口时

按下面的框架标记搜不到入口时，才可以把 README 当作检索线索。这样找到的入口，在打开对应代码之前保持 `inferred`。

技术栈确定后，搜该框架自己的入口标记。下表只是常见例子，不是完整清单。表里没有的框架，先找出它的入口约定，再回到上面的三遍。

| 种类 | 可搜的标记 |
| --- | --- |
| HTTP API | 路由表、控制器、`MapGet` / `MapPost`、`[HttpGet]` |
| 页面 | 前端路由配置、页面组件、菜单项 |
| CLI | 命令注册 |
| 消息 | Consumer、订阅、消息 Handler |
| 定时任务 | Cron、`BackgroundService`、`IHostedService`、Job |
| 桌面 | 主窗体、菜单和按钮事件 |
| 移动端 | Activity、页面、路由 |

## 分工

第一遍完成并分组之后，才考虑子 Agent。宿主真能委派、并且至少有两组互不重叠的入口时，把组派出去。最多 3 个，深度 1。每个子 Agent 只领一组入口，并遵守本文件的下钻深度。

主 Agent 合并清单，并自己核对每条要写入模型的结论。子 Agent 的转述不是已核对事实。不能委派时顺序做完，在索引里说明。
